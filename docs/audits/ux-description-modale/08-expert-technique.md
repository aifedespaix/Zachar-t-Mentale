# 08 — Audit technique (faisabilité, coût, risque, testabilité)

Périmètre : la modale de description (`src/content/DescriptionDialog.tsx`) et son éditeur `src/content/BlockEditor.tsx` (1490 l.).
Rôle : auditeur. Aucun code modifié. Tout ce qui suit est appuyé sur le code lu ; **les hypothèses non vérifiées sont marquées ⚠**.

## Verdict global

L'éditeur est dans un état sain et bien testé (4 suites dédiées, `BlocEditor`, `blocks`, `renderMath`, `descriptionHistory` via `DescriptionDialog`). Les 18 idées se répartissent en trois familles très inégales :

- **Cosmétique / mécanique (~10 items)** : coût S, risque faible, testable en jsdom. À faire sans débat.
- **Comportemental (~5 items)** : coût S/M mais chacun **change une convention déjà écrite dans le code et documentée** (Entrée = nouveau bloc, Tab = enfant sur le canevas, `Ctrl+Entrée` = ouvrir la description). Ce sont des **décisions produit**, pas des tâches.
- **Modèle de données (2 items réels : #8 et #9/#10, plus #16-en-cellule)** : c'est le seul chantier lourd. `CardBlock` (`src/types/cardBlock.ts:27-41`) n'a **aucun type conteneur, aucun champ optionnel, aucune méta**. Le format n'est **pas versionné** (`src/persistence/serialization.ts:13-22` : un tableau nu, ou `{meta,cards}`). Tout nouveau champ/kind traverse : `sanitizeBlock`, `cloneBlock`, `blockToPlainText`, `isEmptyBlock`, `contentOf`, `normalizeContent`, `reconcileCards`, la validation partagée `validateCards`/`repairCards` (utilisée aussi par `admin/`), les 4 `switch (block.kind)` de rendu, et la sync (le `.zmap` entier est un blob texte : `infra/pocketbase-schema.mjs:143`).

Recommandation structurante : **livrer #8 et #9/#10 comme UNE seule fonctionnalité, sans arbre récursif** — un bloc plat `{kind:'question', text}` qui sert d'en-tête, les blocs suivants jusqu'au prochain en-tête lui appartenant par convention de rendu. On obtient le contenant visuel demandé sans toucher à la récursion, au versionnage ni à l'admin. Détail en « Chantier architectural ».

## Chantier architectural (#8, #9/#10, #16-en-cellule)

**Ce qui casse si on ajoute un kind conteneur récursif** (`{kind:'question', children: CardBlock[]}`) :

1. **Type** : `CardBlock` devient récursif → `blockToPlainText`/`isEmptyBlock`/`cloneBlock` doivent traiter `children` récursivement, et les 4 `switch` de rendu (`BlockView.tsx:79`, `BlockEditor.tsx:973`, `blocks.ts:107/126`) deviennent récursifs. TypeScript signalera chaque `switch` non exhaustif : c'est le bon filet, il faut le garder (pas de `default`).
2. **`blocksToPlainText`** : doit aplatir récursivement, sinon `definition` (le miroir dérivé) diverge de `content` — et c'est `definition` que lisent le **quiz** (distracteurs/indices : `types/card.ts:70`, `blocks.ts:333`), le **XMind** (`notes.plain.content`) et le **PDF** (`export/StaticCardView.tsx:85` → `BlockView`).
3. **`normalizeContent`** : la règle « une liste entièrement texte est stockée en `definition` seule » (`blocks.ts:314-323`) n'a plus de sens si un conteneur vide existe → il faut une règle d'élagage récursive, sinon un conteneur vide se sérialise et revient comme une carte « non vide ».
4. **Compatibilité descendante — le vrai danger.** Le format n'a **pas de numéro de version**. Une vieille version qui ouvre un `.zmap` neuf passe chaque kind inconnu dans la branche `default` de `sanitizeBlock` (`blocks.ts:233-241`) : le conteneur est **aplati en texte** (les enfants disparaissent en tant que blocs). Pire : la première écriture sur cette carte (`useCardsStore.ts:136` → `updateContent`) réécrit la liste dégradée, et la structure est perdue **définitivement** — le commentaire de `contentOf` (`blocks.ts:255-260`) l'assume explicitement (« the unknown KIND is gone for good »). Donc oui : c'est un **changement de format de fichier**, avec perte de données chez toute version antérieure, et les fichiers déjà écrits restent lisibles (pas de migration de lecture nécessaire) mais **non ré-écrivables sans perte par une version ancienne**.
5. **Sync PocketBase** : côté serveur, rien à valider (blob texte, `content`), donc pas de rupture serveur. **Mais `admin/` importe le même validateur** : `admin/src/lib/quality.ts:1` → `@app/validation/cardsValidation`, et `salvage()` passe par `normalizeContent(sanitizeBlocks(entry.content))` (`cardsValidation.ts:335`). Une carte à conteneur passée par « Réparer » depuis le panneau prof **ressortirait aplatie** : la réparation détruirait la structure. C'est le point de rupture à traiter avant tout nouveau kind, et il coûte une modification de `admin/` + son propre test.
6. **Migration** : aucune n'est possible *dans* le fichier faute de version. Introduire un `formatVersion` (précédent dans le repo : `syncState.ts:133-136` **refuse** de lire une version future au lieu de la mal interpréter) permettrait à une version ancienne de **refuser d'écrire** plutôt que d'aplatir. C'est la seule protection honnête, et c'est un chantier à part entière (impact `serialization.ts`, `fileStore.ts`, `admin/`, sync).

**Forme recommandée, sans récursion** : un bloc plat `{kind:'question', text, ...}` qui **ouvre un groupe** ; les blocs suivants jusqu'au prochain bloc `question` (ou la fin) sont ses enfants, par convention de rendu (bordure/fond bleu sur la plage). Conséquences : `sanitizeBlock` gagne **un** cas plat, `blocksToPlainText` reste linéaire, le mirroir reste exact, `moveBlock`/`blocksDiffer`/l'undo local ne changent pas, la sync reste opaque, et `admin/` continue de valider. Une vieille version perd **le style**, pas le texte. C'est aussi exactement l'item #8 (champ d'en-tête bleu), donc **un seul lot pour #8+#9+#10**. Coût réaliste : M pour la forme plate, XL pour l'arbre récursif.

**Piège de champ optionnel (vaut pour #8, #9, #16)** : `sanitizeBlock` **reconstruit** chaque bloc champ par champ (`blocks.ts:192-232`). Ajouter une propriété sans l'ajouter à **chaque** branche de `sanitizeBlock` (et à `cloneBlock`, `blocks.ts:168-172`) la fait **disparaître silencieusement** dès qu'une carte touche le chemin de réparation/validation partagé. Test à écrire avant : « un bloc X avec la nouvelle propriété survit à `sanitizeBlocks` ». Idem `TableCell` (`cardBlock.ts:25`) pour #16-en-cellule : le rendu (`BlockView.tsx:190`), `cellText`/`cloneCell`/`cellIsEmpty` (`blocks.ts:4-12`) et les éditions de colonnes (`BlockEditor.tsx:143-245`) doivent suivre, non seulement le type.

## Causes racines confirmées

- **#11 (double champ au chargement)** — `src/content/MathFieldEditor.tsx:103` : `const [showMathField] = useState(() => loaded)`. `loaded` est une variable **module** (`:44`) mise à `true` de façon asynchrone par `loadMathLive()` (`:69-79`, appelé en effet `:141-143`). Rien ne re-rend l'instance montée : `showMathField` reste `false` à vie pour ce bloc. Conséquence : le chemin dégradé — **textarea LaTeX monospace + aperçu KaTeX empilés** (`BlockEditor.tsx:1099-1124`) — reste affiché alors que MathLive est chargé : c'est le « double champ » observé (deux boîtes pour une seule formule). Un **remontage** du composant réévalue `loaded` à `true` → `<div ref={hostRef}/>` (`:188-189`) avec un vrai `<math-field>` : c'est pourquoi l'aller-retour texte → formule « corrige » l'affichage (`replace(index, convertBlock(...))`, `BlockEditor.tsx:571`, change le `case` de `BlockField` et remonte `MathFieldEditor`). Vérifié aussi par le test : `DescriptionDialog.test.tsx:7-12` documente explicitement ce comportement.
  **Correctif le plus sûr** : garder « décidé une fois » comme garde-fou anti-destruction du caret, mais ne plus décider *avant* le chargement. Le bon compromis : `loadMathLive()` est déjà lancé au mount ; n'afficher le *fallback* que lorsque le chargement est **terminé** (succès : monter le champ ; échec : fallback définitif), en conservant une décision figée par une fois résolue, et sans jamais remplacer un champ qui a le focus ou une valeur modifiée depuis le mount. Alternative encore plus sûre et moins invasive : **précharger** `mathlive` (import statique ou `import()` déclenché à l'ouverture de la modale, avant le montage des blocs) — plus de fenêtre d'incertitude, donc plus de fallback visible du tout, au prix de ~5,7 Mo payés à l'ouverture. Tests : (a) montage avant résolution → pas de fallback après résolution ; (b) frappe en cours pendant la bascule → valeur et caret conservés ; (c) échec d'import → fallback et palette fonctionnels (déjà couvert : la suite mocke l'échec).
- **#12 (cellule formule qui ne prend pas la largeur)** — `MathFieldEditor.tsx:188-189` : `<div ref={hostRef} data-testid="math-field" />` **sans style**. Le `field.style.width='100%'` (`:160`) se résout donc contre un hôte qui, dans une cellule de tableau, est un item flex sans `flex:1` ni `min-width:0` (`BlockEditor.tsx:1425`) : le champ se dimensionne sur son contenu, pas sur la cellule — alors que la branche texte/fallback porte `width:100%` (`FIELD_STYLE`, `BlockEditor.tsx:1444/1458`). Correctif local (S) + test de largeur.
- **#14 (libellé « Image » pour un tableau)** — `BlockEditor.tsx:799` : `const current = kind === 'math' ? 'Formule' : kind === 'text' ? 'Texte' : 'Image'` — le ternaire n'a pas de branche `table`, donc tout kind autre que text/math tombe sur « Image ». L'icône, elle, est correcte (`:813`, `Table2`). Le libellé faux se propage à l'`aria-label` (`:805`) et au `title` (`:806-810`), qui annoncent « Ce bloc est en image ». Le *kind* n'est pas perdu (il vaut bien `table`) : c'est purement un ternaire incomplet. En revanche, **le kind d'origine d'un tableau est réellement perdu** (aucun champ de méta dans `CardBlock`), d'où la conversion « retour » qui ne propose que Texte/Formule (`:819-828`) et le « Transformer le tableau en texte » du footer (`:925-929`) — même cause pour l'asymétrie de #16.
- **#13 / conflit d'undo** — `descriptionHistory.ts` est bien une pile **séparée** de `src/state/history.ts` (scope module, par `cardId`, `MAX_DEPTH = 100`, snapshots `CardBlock[][]` complets, `:23-73`). Chaque état est un tableau de blocs **cloné**, donc pas de partage de référence : la profondeur mémoire est bornée par 100 × taille de la description, acceptable. Le handler `Ctrl+Z` de la modale (`DescriptionDialog.tsx:213-222`, `document`, phase bulle) et le dispatcher global (`useGlobalShortcuts.ts:96-121`, `window`, phase **capture**) coexistent : le global s'exécute **en premier**, et `isModalOpen()` (`useGlobalShortcuts.ts:61-67`) ne détecte **pas** cette modale — elle rend `DialogPrimitive.Content` directement (`DescriptionDialog.tsx:240`) **sans `data-slot="dialog-content"`**, contrairement au composant partagé (`components/ui/dialog.tsx:62`). Ce n'est sauvé que par `isTypingTarget` (`:77`) : dès que le focus n'est pas dans un champ (clic sur un bouton de palette, « Raccourcis », un `+` de colonne), un seul `Ctrl+Z` peut **annuler la description ET le document**. À corriger avant d'ajouter des boutons toolbar.

## Bugs / pièges que le demandeur n'a pas vus

1. **La modale est invisible pour `isModalOpen()`** (voir #13). Corollaire pour #3 : `Ctrl+Entrée` = `card.editDescription` (`types/commands.ts:270-274`) peut se déclencher **derrière** la modale ouverte quand le focus est sur un bouton. Deux mots de correction (`data-slot="dialog-content"`) et l'item #3 devient beaucoup moins risqué.
2. **#13 est déjà fait à moitié** : `AppToolbar.tsx:366-367` rend `edit.undo`/`edit.redo` avec `CommandButton` (icône, tooltip, raccourci live, `disabled` calculé), alimentés par `canUndo`/`canRedo` (`useCanvasCommands.ts:60-61`) et testés (`MindMapCanvas.test.tsx:536`). Il manque seulement l'état *description* : `descriptionHistory` n'expose **ni** lecture `canUndo/canRedo` **ni** réactivité (module scope, `:30`). Ajouter des boutons désactivables exige une nouvelle API (`canUndoDescription(cardId)`) + un abonnement (store ou `useSyncExternalStore`). Sans cela, les boutons seront toujours actifs et mentiront.
3. **#3 détruit la convention écrite** : `Entrée` = nouveau bloc est documenté dans `DescriptionDialog.tsx:584` (« Entrée — Nouveau bloc ») et implémenté dans trois champs (`BlockEditor.tsx:1056-1060`, `:1108-1112`, `MathFieldEditor.tsx:163-167`) ; sur le canevas `Entrée`/`Maj+Entrée` = créer un frère, `Tab` = créer un enfant (`types/commands.ts:235,243,251`, `scope:'canvas'`). Enfin `Tab` dans un `<textarea>` **piège le clavier** (WCAG 2.1.2 : toute surface doit offrir une sortie) : je refuserais `Tab` sans alternative documentée.
4. **#5 déplace un ancrage sémantique** : la palette est alimentée par `activeIndex` + `mathFields[activeIndex]` (`BlockEditor.tsx:294-305`), et `insertText` insère **au caret du bloc actif seulement s'il est focus** (`:422-438`). Une toolbar en haut est faisable en réutilisant ces mêmes états (pas de changement de logique d'insertion), mais elle réintroduit « une barre qui agit sur un bloc qu'on ne regarde pas » — exactement ce que le commentaire d'en-tête de `BlockEditor` (`:273-283`) dit avoir supprimé. Le `mathFields` est indexé par **index de bloc** : toute réorganisation/algorithme de drag doit préserver cette correspondance (aujourd'hui les `key` sont les index, `:511`, ce qui « marche » mais interdit de réordonner en animant les nœuds).
5. **#2/#15 et HTML5 DnD** : le DnD actuel est natif (`BlockEditor.tsx:516-528`, `:700-718`). `setDragImage` (`:709`) fige une **image bitmap** de l'élément : elle n'est pas mise à jour pendant le drag, donc **aucun aperçu live**, et les blocs voisins ne s'animent pas (les navigateurs ne garantissent ni `rAF` ni transitions pendant un drag natif). L'ordre n'est appliqué qu'au `drop` (`:523-528`) : la FLIP « montrer où ça va » est donc **hors de portée du natif**. Deux chemins : (a) **garder le natif** et animer **après** le drop avec ce qui est déjà là — `motion/react` est **déjà** une dépendance et déjà utilisé (`CardNode.tsx:2`, `RecallDialog.tsx`, `QuizSummaryModal.tsx`) : coût S/M, aucun paquet à installer, mais pas d'aperçu live ; (b) **basculer sur pointer events + FLIP/`motion`** (aperçu live + auto-scroll + tactile) : M/L et c'est une **réécriture** du DnD (le natif gère gratuitement tactile, clavier, drag hors fenêtre). `dnd-kit`/`react-aria` ne sont **pas** dans `package.json` (`:21-47`) : je ne les ajouterais pas sans besoin démontré, `motion` suffit pour la FLIP. `document.startViewTransition` est disponible et **déjà utilisé avec garde** (`theme/circularReveal.ts:23-30`, garde `prefersReducedMotion()` + test) : WebView2 étant un Chromium evergreen, c'est utilisable — mais une transition de vue sur une liste éditable est plus risquée qu'une FLIP ciblée. Tests : jsdom **n'implémente pas** `DataTransfer` ; il faudra un test unitaire de `moveBlock` + un test pointer-based, sinon rien n'est testable (aujourd'hui **aucun test ne couvre le drag** : seuls les boutons ↑/↓ le sont, `DescriptionDialog.test.tsx:226-255`).
6. **#15 est déjà à moitié là** : les `+` par colonne existent (`:1274-1284`) et par ligne (`:1370-1379`), mais **pas avant la première colonne** (la cellule de coin est un `<div/>`, `:1273`) **ni avant la première ligne** (la poignée de la ligne *i* insère *après* la ligne *i*, `:1375`). Le « + aux extrémités » demandé n'est donc pas un ajout, c'est un **décalage d'un cran** : à spécifier (sinon on obtient deux `+` côte à côte).
7. **#6 : le modèle accepte, le rendu non.** `latexToPlainText` écrase déjà tous les blancs, `\n` compris (`blocks.ts:103`) : un retour à la ligne dans `latex` ne casse pas le mirroir mais **disparaît** du quiz/XMind/PDF. Et KaTeX traite un `\n` en math mode comme un espace : « Entrée va à la ligne » n'aura d'effet visuel qu'avec un environnement (`\displaylines{}`, `aligned`, `cases`) — sinon l'utilisateur verra le curseur descendre et rien changer à l'écran. ⚠ Je n'ai pas exécuté MathLive (il est mocké en échec dans les tests, `DescriptionDialog.test.tsx:13`) : sa gestion multi-ligne réelle reste **non vérifiée**.
8. **#17 : ~15 attributs `title=` et non mécanique.** Recensés dans `src/` : `BlockEditor.tsx:760,806,1469`, `MathPalette.tsx:284`, `LanguageHelpPalette.tsx:219`, `DescriptionDialog.tsx:289,533`, `AppToolbar.tsx:444`, `QuizConfigModal.tsx:112`, `SyncSettingsPanel.tsx:364`, `FileTreeRow.tsx:626,682,721,799,822`, `FileSidebar.tsx:628`, `RecentFilesList.tsx:174` (`CardNode.tsx:1193` et `SettingsSection.tsx:141` ne sont **pas** des tooltips : title de contenu/prop de composant). Pièges réels : (a) `TooltipContent` est un `Portal` en `z-50` (`tooltip.tsx:39-51`) et le contenu de la modale porte `zIndex: 50` (`DescriptionDialog.tsx:265`) — **égalité de z-index**, l'ordre du DOM décide : à vérifier au pixel, risque d'infobulle sous la modale ; (b) `delayDuration={0}` + `disableHoverableContent` : infobulles instantanées partout, bruit visuel et flicker au survol de la grille du tableau ; (c) un `<button disabled>` ne reçoit pas les événements : les infobulles des actions désactivées (← #13) ne s'afficheront pas sans conteneur `asChild` non désactivé ; (d) Radix Tooltip exige un `TooltipProvider` (présent dans `CardNode.tsx:35`, à vérifier ailleurs) ; (e) les tests qui interrogent un bouton par son nom accessible devront être vérifiés un par un si le `title` disparaît.
9. **#18 crée une carte depuis une modale qui ne peut pas la montrer** : les commandes de création sont `scope:'canvas'` et gardées par `editable`/`locked` (`useCanvasCommands.ts:83-94`) ; la modale est `key={cardId}` et se remonte à chaque navigation (`DescriptionDialog.tsx:105-109`). Créer un frère « depuis » le dialogue change la carte sous le dialogue : à trancher (naviguer ? fermer ?). Risque double avec le point 1 (`Ctrl+Entrée`).

## Ordre d'implémentation recommandé

**Lot 0 — hygiène (avant tout le reste, S)** : `data-slot="dialog-content"` sur le `DialogPrimitive.Content` de la modale + test « les raccourcis globaux sont inertes quand la description est ouverte ». Sans lui, #3, #13 et #18 se construisent sur un socle faux.

**Lot 1 — bugs confirmés, zéro décision produit (S)** : #14 (ternaire `:799`), #12 (width du host), #11 (init MathLive ; option « précharger » à trancher ici, c'est le seul arbitrage coût/perf).

**Lot 2 — gains mécaniques indépendants (S, parallélisables)** : #4, #7 (couplé à #11), #1, puis #17 par fichiers (une PR par écran, `tooltip.tsx` en premier avec le test de z-index dans la modale).

**Lot 3 — toolbar (M)** : #13 (API `canUndo/canRedo` + réactivité dans `descriptionHistory`, puis `CommandButton`), puis #5 (réutilise `activeIndex`/`mathFields`), puis #15-partie-1 (les `+` aux extrémités), puis #16-côté-bloc. #13 avant #5 parce que les deux se disputent le haut de la modale.

**Lot 4 — décisions produit à documenter d'abord** : #3 (Entrée/Ctrl+Entrée/Tab + `ShortcutsPanel` + docs), #6 (convention de multi-ligne + mirroir), #2/#15-DnD (natif + FLIP, ou réécriture pointer), #18.

**Lot 5 — modèle, un seul lot** : #8+#9+#10 sous **forme plate** (bloc `question` ouvrant un groupe), avec : tests de survie `sanitizeBlock`, test « une vieille version aplatit mais ne perd pas le texte », et décision explicite sur `formatVersion`. L'arbre récursif n'entre qu'après cette décision.

## Ce que je refuserais de faire sans spec

1. **`Tab` = changer le type de bloc** (#3) : piège clavier dans un `<textarea>`, contradiction avec `Tab` = enfant sur le canevas. Il faut une touche de sortie documentée ou une autre touche.
2. **Toute bascule rétroactive entrée↔nouveau bloc** (#3, #6) sans mise à jour simultanée de `ShortcutsPanel` (`DescriptionDialog.tsx:584-589`), des commentaires de contrat et des tests — sinon la doc intégrée ment.
3. **Un `kind` conteneur récursif** (#9/#10) sans : décision sur le versionnage du format, protection « refuser d'écrire » pour les versions anciennes, et alignement de `admin/` (`quality.ts:1`, `cardsValidation.ts:335`). Sinon on livre une perte de données silencieuse chez l'élève qui n'a pas mis à jour.
4. **Un nouveau champ de bloc** (#8, #9, #16-en-cellule) sans test de survie à `sanitizeBlocks` : le chemin de réparation partagé le supprime silencieusement.
5. **Un aperçu live de drag** (#15) sans trancher natif vs pointer events : les deux ne coûtent pas la même chose et n'ont pas les mêmes limites (tactile, clavier, auto-scroll). Et sans test : aucun test de drag n'existe aujourd'hui.
6. **Créer des cartes depuis la modale** (#18) sans définir ce que devient la modale (navigation, historique, carte verrouillée).
